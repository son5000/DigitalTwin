# 프로젝트 ZIP·서버 저장 및 복수 스캔 계약

## 복원 범위

에디터의 `serializeLayout()` 결과 전체를 `project.json`에 보관한다. 여기에는 설비·서랍 치수, 문별 스캔 정합, 센서·ROI, 이미지 보정, 가상 카메라, 시작 시점, 표시 설정이 포함된다. ZIP의 `files/`에는 업로드한 설비 원본 묶음(OBJ/MTL/이미지 또는 PLY), 등록한 텍스처, 커스텀 자산, 인라인 대표 이미지가 들어간다. ZIP은 파일별 크기·CRC를 검사한 뒤 새 프로젝트로 등록한다. 가져올 때 프로젝트·자산 ID를 새로 발급하고 내부 참조 및 센서 보정 서명을 갱신한다.

ZIP에 담기지 않는 것은 앱 빌드의 기본 제공 리소스, 외부 HTTP URL의 실제 내용, 실시간 측정값과 백엔드의 센서·사용자 계정이다. 따라서 동일한 앱 빌드와 외부 데이터 공급원이 있어야 실제 관측까지 재현된다. 업로드 원본이 브라우저 저장소에서 사라졌다면 내보내기를 실패시켜 불완전한 ZIP을 만들지 않는다.

## 서버 API

`VITE_MONITORING_API_BASE`가 설정되면 에디터의 **서버로 전송**이 `PUT /projects/{projectId}/bundle`에 `Content-Type: application/zip`으로 동일한 ZIP을 보낸다. 성공 응답은 `{ "projectId": "요청한 ID", "revision": 1 }` 형식이다. 서버는 ZIP의 모든 파일과 JSON을 검사하고 파일 저장·DB 참조를 한 트랜잭션으로 확정한 뒤 응답해야 한다. 일부 파일만 저장됐으면 성공으로 응답하지 않는다. 현재 백엔드가 없어 실제 업로드·재조회는 검증되지 않았다.

다른 PC의 서버 뷰어에서 보려면 `GET /projects/{projectId}`가 레이아웃을 반환하는 것과 별도로 업로드 파일을 제공해야 한다. 설비 스캔의 `sourceType: UPLOAD`는 그 PC의 IndexedDB에만 있으므로, 서버 응답에서는 각 OBJ/PLY의 `sourceKey`, MTL의 `relatedSourceKey`, 이미지의 `textureSourceKey`를 접근 가능한 서버 경로로 바꾸고 `sourceType: SERVER_KEY`를 사용해야 한다. MTL이 상대 경로로 참조하는 이미지들도 같은 경로 구조로 제공해야 한다. `textureAssetId`로 참조하는 사용자 텍스처와 원본 기준 사진도 서버에서 복원할 수 있어야 한다. 이 파일 제공·재조회 계약이 구현되기 전에는 **서버 전송 성공만으로 다른 PC의 뷰어 재현을 보장할 수 없다.**

## 복수 스캔 운영

한 설비의 여러 문에 연결된 스캔은 선택한 설비에서만, Worker로 한 파일씩 파싱한다. 첫 파일부터 화면에 붙이고 나머지는 순차 추가하며, 숨긴 탭은 렌더링을 쉬고 복수 스캔이 보이는 동안 최대 약 30fps·최대 1.5 배 픽셀 비율로 렌더링한다. ZIP 가져오기는 STORE 파일의 CRC만 청크로 검사하고 원본 ZIP의 Blob 슬라이스를 사용한다.

스캔 개수보다 **파일별 삼각형·점 개수, 텍스처 해상도, GPU 메모리**가 실제 한계를 결정한다. 임의의 대용량 N개 파일을 모든 PC에서 보장할 수는 없다. 납품 시 대표 설비의 최대 구성으로 브라우저 메모리·프레임률을 측정하고, 필요한 경우 스캔 제작 단계에서 메시·텍스처 용량을 줄인 전시용 사본을 준비한다. 원본 파일은 ZIP에 그대로 보관한다.
